# 01 — Architecture & Storefront Reference

Studio Deny: a streetwear e-commerce storefront + admin CMS. TanStack Start (React 19) frontend, Supabase (Postgres + Auth + Storage + Edge Functions) backend, Cloudinary for media, Razorpay for payments, Shiprocket for shipping, Meta WhatsApp Business API for customer notifications. No server of its own beyond Supabase and its edge functions — this is a fully static-hostable SPA (deployed to Vercel) talking directly to third-party backends from the browser.

## 3. `__root.tsx` and the provider tree

`src/routes/__root.tsx` is the actual app shell (`createRootRoute`). Two things worth knowing:

1. **Conditional smooth-scroll**: `RootComponent` checks `location.pathname.startsWith("/admin")` and only wraps non-admin routes in `<SmoothScroll>` (a Lenis wrapper). Admin pages render without Lenis smooth-scroll — this is why admin table/scroll behavior feels "native," and why `data-lenis-prevent` attributes matter on storefront elements that need normal scroll (modals, drawers) sitting inside the Lenis-controlled tree.
2. **Provider nesting order** (outermost to innermost):
   ```
   AuthProvider
     Preloader (renders itself full-screen while active, not really a "provider" but sits at this level)
     WishlistProvider
       CartProvider
         QuickAddProvider
           { AnnouncementBar + Navbar (non-admin only) }
           <Outlet /> (page transition via framer-motion AnimatePresence, keyed by pathname)
           { Footer + CartDrawer + scroll-to-top button (non-admin only) }
         Toaster (sonner, heavily re-styled to match the site's mono/uppercase aesthetic)
   ```
   `CartProvider` being nested inside (i.e. rendered after, so it can call) `WishlistProvider`'s tree doesn't itself create a dependency, but **`CartProvider` does call `useAuth()`** (it needs to know the logged-in user to decide whether to persist to Supabase) — so `AuthProvider` being the outermost wrapper is load-bearing, not incidental. Admin routes render **only** `<RootContent>` directly (skip the Lenis wrapper) but still go through the exact same provider stack — an admin session still has a cart/wishlist/auth context available, even though admin pages don't use them.
3. `seedIfEmpty()` (`src/lib/seed.ts`) runs once on mount — **this is dead legacy code**: it seeds a hardcoded dummy product list into `localStorage` (`sd_products_custom`), a pattern from before products moved to Supabase. `productsStore.ts` reads/writes the real `products` table now, not this localStorage key, so this seeding has no observable effect on the live storefront — it's a harmless no-op holdover, not a bug, but also not doing anything useful anymore.

## 4. Context providers (`src/context/`)

| Context | Persistence | Notes |
|---|---|---|
| `AuthContext` | Supabase Auth (session in `sessionStorage`, not `localStorage` — see §7 for why) | `signup(email, password, name, phone)`, `login`, `loginWithGoogle`, `logout`. Role resolution (`admin`/`user`) via `supabase.rpc("get_my_role")` on every `onAuthStateChange` event — `INITIAL_SESSION` is the only event that flips `loading` to false, avoiding a race with a separate `getSession()` call. |
| `CartContext` | **Hybrid**: guests get pure in-memory React state (nothing persists across a refresh); logged-in users get their cart written through to Supabase's `carts`/`cart_items` tables, with a merge-on-login step for anything added before login completed. Items with no real `product_variants` row (legacy no-variant products) can't be persisted — an accepted, narrow limitation. | Mirrors `WishlistContext`'s guest/logged-in split, added specifically to make abandoned-cart detection possible (a guest has no phone number to ever notify, so there was never a reason to persist their cart). |
| `WishlistContext` | **Hybrid**: guest → `localStorage` (`sd_wish`); logged-in → Supabase `wishlist_items`, with the same merge-on-login pattern `CartContext` copied. | The template this project's persistence pattern is based on — read this one first if you need to understand the guest/logged-in split shape. |
| `QuickAddContext` | No persistence of its own — ephemeral UI state for the "quick add" modal/floating-card that opens from a product card without navigating to the full PDP. | Renders a `MobileFloatingCard` or `DesktopModal` depending on `useMediaQuery` breakpoints (`<768px` mobile, `768–1023px` tablet, `≥1024px` desktop treated as the modal path too). Fetches per-product variant stock live via `getVariantStock()` when opened. Locks body scroll + Escape-to-close while active. |

## 5. Design system (`src/styles.css`)

No separate Tailwind config — Tailwind v4's `@theme inline` block inside this one file defines every design token, mapped from plain CSS custom properties on `:root`:

```css
--background: #E2E2E4   --foreground: #111111   --surface: #D5D5D8
--primary: #111111      --primary-foreground: #E2E2E4
--secondary: #D5D5D8    --secondary-foreground: #111111
--muted: #C7C7C3        --muted-foreground: #4A4844
--border: rgba(0,0,0,0.18)
--accent: #E0202A       --accent-foreground: #FFFFFF
```
**⚠️ `--secondary` and `--surface` are the exact same value (`#D5D5D8`)** — any element using `text-secondary` on a `bg-surface` background is invisible (identical color on identical color), not just low-contrast. This is a real, confirmed bug found during this project's build (e.g. it made an order's status text disappear on `order.$id.tsx`'s payment card) — not fixed as of this document, flagged for a future pass. If you're asked to build something using `text-secondary`, check what it's sitting on top of first.

Fonts: **Anton** + **Bebas Neue** for `--font-display` (headings, loaded via Google Fonts `@import`), **Barlow** for both `--font-body` and `--font-mono` (there is no real monospace font in use — `.text-mono` is a tracking/sizing convention, not an actual monospace typeface). `color-scheme: light` is hardcoded — **this is a light-only design**, no dark mode toggle or `prefers-color-scheme` handling exists anywhere.

Notable utility classes defined here (used throughout, not shadcn defaults): `.text-display`/`.text-mono` (font family shortcuts), `.glow-primary`/`.glow-lime` (box-shadow glow effects), `.btn-shimmer` (a diagonal light-sweep hover animation on primary CTAs), `.btn-fill`/`.btn-fill-bg`/`.btn-fill-front`/`.btn-fill-back` (a border-button-fills-solid-on-hover effect with clip-path text-swap, `--light`/`--dark` variants), `.editorial-nav-link` (underline-grows-from-left-on-hover, and supports a `data-status="active"` state for the current route), `.img-editorial-reveal` (fade+scale-in entrance animation), `.ticker-scroll` (the marquee/announcement-bar infinite scroll). Global button hover behavior (`transform: translateY(-3px)`, letter-spacing widen, shadow) is applied to **every** `<button>` site-wide via a base-layer selector, not per-component — a new button doesn't need to opt into this, only actively override it if a different feel is wanted. All animations respect `prefers-reduced-motion: reduce`.

## 6. `src/lib/` — the data-access layer

Verified in depth this session (read in full):
- **`supabase.ts`** — the single `supabase` client instance, typed against `Database` (`src/types/database.ts`). **Auth tokens are stored in `sessionStorage`, not `localStorage`** — a deliberate choice so a session doesn't persist across browser-close on a shared/public device.
- **`orders.ts`** — `Order`/`OrderStatus` types, `mapRow()` (DB row → camelCase `Order`), `listOrders`, `ordersFor(email)`, `getOrder`, `createOrder`, `updateOrderStatus`, `cancelOrder` (→ `shiprocket-cancel`), `refundOrder`, `updateInvoice`, `createShipment` (→ `shiprocket-sync`), `requestReturn` (→ `shiprocket-return`), `createReplacementOrder`. Full detail in 05-SHIPPING-SHIPROCKET.md.
- **`productsStore.ts`** — `Product` type, `listProducts` (storefront, active-only), `getStoredProduct(slug)`, `upsertProduct`, `deleteProduct`, `setProductActive`, `getVariantStock(slug, fallbackSizes)` (the storefront's stock-aware size list, falls back to "all in stock" for products with zero variants), `listAllAdminProducts`, `getVariantStockTotals()` + `effectiveStock()` (added to fix the stale-flat-stock-field bug documented in 02-DATABASE-SCHEMA.md).
- **`razorpay.ts`**, **`cloudinary.ts`** — see 04-PAYMENTS-RAZORPAY.md and the Cloudinary summary below.
- **`rateLimit.ts`** — `checkRateLimit`/`recordAttempt`/`clearRateLimit`/`formatMs`, **100% `localStorage`-based**, keyed as `rl_{key}`. This confirms the `rate_limits` Postgres table (02-DATABASE-SCHEMA.md) is genuinely unused infrastructure — nothing in the app ever reaches it.
- **`settings.ts`** — loyalty/discount/shop config, `localStorage` key `sd_settings_v1`. Defaults: entry threshold ₹5,000, ₹50 spent = 1 point earned, 1 point = ₹1 at redemption, free shipping over ₹2,499, per-tier discount percentages (ROOKIE 0% / RUNNER 5% / RIOT 10% / LEGEND 15%). **This is the client-side loyalty config that disagrees with the DB's own thresholds** — see 02-DATABASE-SCHEMA.md's `loyalty_balances` entry for the full mismatch. Also exports `getInvoiceTemplate`/`saveInvoiceTemplate` — the invoice template itself moved to a real Supabase singleton (`invoice_settings`, 02-DATABASE-SCHEMA.md) since it used to live in this same localStorage key, which broke it for any customer viewing their own invoice on their own device.
- **`sectionHeadings.ts`** — `useSectionHeading(key, fallbackText, fallbacks?)`, backing the `section_headings` table (02-DATABASE-SCHEMA.md). Batches all headings into one query, cached at module scope so N components on one page cost 1 query total, not N.
- **`seed.ts`** — dead legacy localStorage product seeder, see §3.

Not re-verified line-by-line this pass (inferred from name + call-site context — read directly before relying on exact behavior): `catalog.ts` (categories/brands CRUD — `listCategories`, `listTopLevelCategories`, etc., confirmed real and Supabase-backed per earlier work in this project, `Brand` type still localStorage-backed per that same earlier finding), `sizes.ts` (likely the `sizes` table CRUD backing the category-scoped size picker), `megaMenu.ts` (likely `mega_menu_*` table CRUD), `navCollections.ts` (likely navbar category data derivation), `notifications.ts` (admin bell "last seen" `localStorage` timestamp helper — `getLastSeen`/`markSeen`, used by `admin.tsx`), `reviews.ts` (product review data, backing the `Reviews` component on the PDP), `seo.ts` (`buildMeta`/`buildLinks`/`orgJsonLd`/`websiteJsonLd`/`productJsonLd`/`breadcrumbJsonLd` — meta tag + structured-data helpers, confirmed used in `index.tsx`/`product.$slug.tsx`), `loyalty.ts`, `products.ts` (note: **different file from `productsStore.ts`** — likely an older/legacy type definition file `seed.ts` imports from; don't confuse the two).

## 9. Build & deploy

- `npm run dev` — Vite dev server. `npm run build` — production build (this project's own verification workflow always runs it as `NODE_OPTIONS=--max-old-space-size=4096 npx vite build`, since the default Node heap limit isn't enough for this build). `npm run preview` — serve the built output locally.
- **Deployed to Vercel** — env vars set in the Vercel project dashboard. `VITE_`-prefixed vars are safe to expose (bundled into the client): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_RAZORPAY_KEY_ID`, `VITE_CLOUDINARY_CLOUD_NAME`, `VITE_CLOUDINARY_UPLOAD_PRESET`. **Never** put a real secret (Razorpay secret key, Shiprocket password, WhatsApp token) in a `VITE_`-prefixed var — those all live in Supabase Edge Function secrets instead (07-EDGE-FUNCTIONS-AND-SECRETS.md).
- Standard verification sequence used throughout this project's history before every commit: `npx tsc --noEmit -p .` → `NODE_OPTIONS=--max-old-space-size=4096 npx vite build` → both must pass clean before committing.
- Git: two `gh` accounts exist on the dev machine historically — `PavanSuryaChintada` (write access) and `anuraj-bellcorpstudio` (no write access, causes 403 on push if active). If a push ever 403s, `gh auth switch --user PavanSuryaChintada`. The GitHub remote itself has moved to `https://github.com/StudioDeny/studio-deny.git` (old remote URL still redirects and works, but is stale).

## 10. Cross-cutting gotchas (confirmed still accurate)

1. **`Cannot find name 'Deno'` in editor for `supabase/functions/*.ts`** — false positive, that folder is outside `tsconfig.json`'s `include`. Not a real error, ignore it.
2. **No Supabase CLI in the dev environment; `supabase/config.toml` points at a stale, dead project ref** (`ylnulbqctvvvvygezyik`) — the real project is `ablejcrtuiohdrapgacb`. Every migration and every edge function deploy in this project's history has gone through the Supabase Dashboard by hand. See 07-EDGE-FUNCTIONS-AND-SECRETS.md §1.
3. **`--secondary` === `--surface`** (§5) — a real, unfixed contrast bug, not a design choice.
4. **Two disagreeing loyalty-tier systems** (client `lib/settings.ts`+`lib/loyalty.ts` vs. the DB's `recalc_loyalty_tier()`) — see 02-DATABASE-SCHEMA.md.
5. **Auth session lives in `sessionStorage`** — a returning user who closed their browser (not just the tab) will need to log in again. This is intentional (shared-device safety), not a bug, but worth knowing if "why did I get logged out" ever comes up.
